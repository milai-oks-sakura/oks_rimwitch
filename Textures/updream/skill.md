# RimWorld 像素美术（Updream 画布版）

## 0. 运行边界（最高优先级）

```text
本 Skill 在 Updream 中运行时：
1. 文字正式产物（风格基准、强度等级清单、评审报告）使用 canvas_text_create。
2. 图片正式产物（物品/建筑/植物/动物/角色/图标）使用
   canvas_generation_prepare -> canvas_generation_select -> canvas_media_create。
3. 节点状态使用 canvas_status_manage(operation="get") 查询。
4. 媒体节点创建后使用 canvas_status_manage(operation="update") 完成两步自动命名。
5. 不能调用的能力必须报告 blocked/degraded，不用聊天文本、本地文件路径或虚构 URL 冒充画布产物。
6. 一切字段以当前实时工具 schema 为准；本 Skill 中的调用示例只表达意图，不覆盖 schema。
```

三条不可跨越的红线：

- 聊天里写出提示词、或本地存了一张 PNG，都不等于“已落画布”；
- `canvas_media_create` 返回 `node_id` 只证明节点已创建/已提交，不证明“已生成”，更不证明“质量通过”；
- 不创建通用 Plan、工作项、Checklist 或 `w1` 之类的 ID；媒体选参返回的 `plan_id` 只是本轮选参令牌，原样回传，不当业务 Plan 用。

领域观念（决定后面所有取舍）：**RimWorld 的画面之于游戏，就像字体之于小说。** 画面是让玩家在脑中讲故事的工具，不是展示对象；图形是抽象化的图标，不是写实插画。总原则是**用最少的投入换最大的收益**，细节不是价值，能被读懂的细节才是价值。

## 1. 目标

把用户的像素美术需求变成**可被下游继续引用的画布产物**：

1. 先给出一份可复用的《全局美术风格基准》文字节点（强度层级 + 描边规则 + 画布规范 + 负向边界），供后续所有素材引用；
2. 按“一个实体一个任务”生成像素素材图片节点，并把游戏内可读性作为通过条件；
3. 对已有素材给出评审结论文字节点，结论必须能逐条回溯到真实节点与可检查事实；
4. 每个停顿点都告诉用户：现在什么状态、下一流程是什么、在画布哪里操作、输入哪个动作词继续。

## 2. 触发与不触发

**触发**（满足任一）：

- 要求按 RimWorld / 香草风格绘制或生成 mod 的物品、建筑、墙、地板、植物、动物、角色或 UI 图标；
- 要求判断某张素材在游戏缩放下是否可读、是否“属于”原版画面；
- 要求把写实插画风素材改造成 RimWorld 像素图标风；
- 要求整理一份可复用的 RimWorld 像素美术规范/评审清单。

**不触发**（或不接管）：

- 只做纯写实插画、概念图、宣传海报，且明确不要像素化 → 说明本 Skill 只覆盖像素图标语境，询问是否仍按 RimWorld 风格；
- 要求生成 3D 模型、动画序列帧、着色器、Unity/XML 代码 → 这些不是画布图片产物，告知超出范围，不用图片节点冒充；
- 用户只想要文字建议、明确不要画布产物 → 可以只交付文字节点，并在回执中声明 `canvas_delivery=degraded`（无图片节点）。

## 3. 输入与真实引用

### 3.1 可以作为引用的值

- 当前对话中真实存在的用户上传图片句柄（如 `img:1`）；
- 平台返回且当前工具可读取的真实 URL；
- 已存在、已完成、内容验收通过的画布图片节点 ID；
- 本轮前序任务真实返回的结果。

### 3.2 不能作为引用的值

本地路径（`Textures/...`、`D:\...`）、压缩包内文件名、Markdown 图片名、旧对话里记住的 ID、自行拼出的 URL、以及**任何 text 节点**。风格基准、评审报告、强度等级清单都是文字节点，把它们当图片引用是无效引用——它们的内容必须完整写进 `prompt`，来源用文字节点 ID 记录。

### 3.3 输入检查

| 输入 | 检查 | 不满足时 |
| --- | --- | --- |
| 参考图句柄 | 当前上下文能解析 | `blocked`，请用户重新上传，不猜 URL |
| 素材名与用途 | 能确定它是物品/建筑/植物/动物/角色/图标 | 先问一次归属类别，再定强度等级 |
| 目标尺寸需求 | 默认 128×128 正方形画布、游戏内缩放到 64×64 | 用户指定其他尺寸时按用户值，但必须在 prompt 与验收中同步改写 |
| 已有节点 | 用 `canvas_status_manage(get)` 确认真实状态 | stale 或未完成的节点不进 `source_node_ids` |

内部记录（不必全部展示给用户）：`asset_id`、`asset_version`、`display_name`、`target_node_name`、`source_refs`、`depends_on_versions`、`canvas_node_id`、`asset_node_id`、`task_key`、`task_status`、`result_url`、`generation_status`、`quality_status`、`failure_code`、`next_user_action`。

## 4. 画布产物与节点命名

### 4.1 产物表

| 产物 | 节点类型 | 创建方式 | 完成的最低证据 |
| --- | --- | --- | --- |
| 全局美术风格基准 | text | `canvas_text_create` | 同时返回 `canvas_node_id` 与 `asset_node_id` |
| 美术强度等级清单 | text | `canvas_text_create` | 同上 |
| 素材像素图（物品/建筑/植物/动物/角色） | image | `prepare → select → media_create` | 真实 `node_id`，不在 `failures`，`task_status=completed` 且 `cover_url` 非空 |
| UI 图标 | image | 同上 | 同上（另需小尺寸可读性验收） |
| 像素美术评审报告 | text | `canvas_text_create` | 同时返回 `canvas_node_id` 与 `asset_node_id` |

文字节点正文要写完整内容，不能写“详见聊天记录”、占位符或摘要。有多个实体时使用稳定 ID 一一对应：`STYLE_01`（风格基准）、`PROP_01`（物品）、`BLD_01`（建筑）、`PLANT_01`（植物）、`ANIM_01`（动物）、`PAWN_01`（角色）、`ICON_01`（图标），版本从 `@v01` 起。

### 4.2 节点命名模板

| 产物 | 名称模板 | 例子 |
| --- | --- | --- |
| 全局风格基准 | `全局美术风格基准` | `全局美术风格基准` |
| 强度等级清单 | `美术强度等级清单` | `美术强度等级清单` |
| 物品图 | `<物品名>像素物品图` | `铜制怀表像素物品图` |
| 建筑图 | `<建筑名>像素建筑图` | `熔炉像素建筑图` |
| 植物图 | `<植物名>像素植物图` | `夜光苔像素植物图` |
| 动物图 | `<动物名>像素动物图` | `雪原狼像素动物图` |
| 角色图 | `<角色名>像素角色图` | `林默像素角色图` |
| UI 图标 | `<功能名>UI图标` | `法力值UI图标` |
| 评审报告 | `<素材名>像素美术评审报告` | `熔炉像素美术评审报告` |

禁止使用“文本1”“结果”“草稿”“待定”这类无意义名称。质量不通过时改名为 `未采用-<目标名称>-<主要原因>`。

### 4.3 媒体节点两步命名

媒体创建接口通常不能在请求里传显示名称。拿到真实 `node_id` 后，必须**同一轮**完成两步命名：

```text
canvas_status_manage(operation="update", node_id=<真实 ID>, name="<目标名称>", confirmed=false)
canvas_status_manage(operation="update", node_id=<同一 ID>, name="<目标名称>", confirmed=true)
```

命名失败时：报真实节点 ID 与失败状态，该节点不得作为正式下游输入；不要为了“命名”再生成一张图。

### 4.4 布局（画布支持时）

风格基准文字节点放在左侧/顶部；同批素材图按流程方向横向排列；同一资产的各版本纵向相邻；节点尺寸与间距固定，命名变长不应导致布局跳动。当前 API 不支持位置/尺寸字段时不要伪造字段，保留语义名称与依赖关系即可。

## 5. 领域规则（必须写进 prompt 与验收）

### 5.1 五条风格标准

1. **不丑**：至少达到“看着不难受”的审美底线；丑陋画面会直接劝退玩家。
2. **易识别**：一眼能看出它是什么、正在发生什么；可识别性优先于美观。
3. **低噪音**：简化形体、减少高频细节。一屏可能同时存在上百个物体，满屏细节会让“什么重要”无法扫描。
4. **强度层级**：与故事相关的抓眼，次要的让视线滑过去；层级**主要由描边建立**，不是靠细节量。
5. **快速实现 + 留白**：砍细节、扩内容，只保留推动故事所需的细节；形体留出可被玩家自由解读的余地（收纳架哪面朝上、镰刀机的确切形体，玩家自己会补完）。

### 5.2 描边与强度层级（硬性规则）

| 类别 | 描边 | 效果 |
| --- | --- | --- |
| 角色（Pawn） | 2–3 px 纯黑，最粗 | 全场最跳，视线第一落点 |
| 物品 / 建筑 / 墙 | 2–3 px 黑实线 | 明确、干净、可辨识 |
| 植物 | 深绿色描边，或无描边 | 微微融入背景；成片树林会“糊”在一起，让角色凸显 |

同一画面里不要给所有东西一样的描边粗细与颜色——层级差就是靠这个拉开的。

### 5.3 制作规范

- **画布**：正方形。游戏把物品贴图缩放到 64×64，所以在 **128×128** 上作画最舒适。画布越大、或像素画得越小，物品在游戏里就显得越小。
- **构图偏移**：需要偏心构图时用**补白（padding）**，不要移动主体。
- **底色层**：最底层垫一层完全不透明黑、约 **1% 不透明度**，压掉边缘漏出的白像素（alpha 白边）。
- **少用/不用黑色内线**：反向描边（inner line）不要用黑色，用**明暗与色差**表达结构。
- **细节预算**：宽度小于 **3 px** 的细节基本看不见，除非有很强颜色对比，否则不要画。
- **不追求写实、不追求炫技**：不用亮闪闪特效或高对比装饰把注意力从故事上引开。

### 5.4 负向边界（写进每个 prompt）

不要写实纹理、不要渐变光晕、不要锐利高光、不要多余黑色内线、不要小于 3 px 的低对比细节、不要水印/Logo/签名、不要文字、不要给植物画粗黑边、不要非 1:1 画幅、不要主体被裁切或缩到画布一角。

## 6. 执行流程

### 阶段 0 · 判定意图与强度等级

先问一句领域问题（不是流程确认门）：**这个东西在故事里承担什么？** 据此确定强度等级（角色 / 物品·建筑 / 植物），并写入 `asset_id`、`asset_version=v01`、`intensity`。一次只处理一个实体。

### 阶段 1 · 风格基准落画布（可复用）

若画布上没有可用的风格基准，创建文字节点 `全局美术风格基准`（`STYLE_01@v01`），正文含：五条标准、描边层级表、128×128 画布与 1% 黑底、3 px 细节门槛、负向边界、验收清单。同时把本批实体的强度等级写成 `美术强度等级清单`（可选）。返回必须同时含 `canvas_node_id` 与 `asset_node_id`，否则状态只能是 `partial`/`blocked`，不得说“已落画布”。

### 阶段 2 · 素材生成（每次一个实体）

```text
canvas_generation_prepare(tasks=[{
  "task_key": "<ASSET_ID>_<VIEW_OR_ROLE>",     // 例：PROP_01_ICON
  "node_type": "image",
  "prompt": "<完整提示词：实体名+强度等级+描边规则+画布规范+负向边界+STYLE_01@v01 摘要>",
  "reference_images": ["<真实句柄或 URL，可为空>"],
  "source_node_ids": ["<已完成的 image 节点 ID，可为空>"],
  "position": {"x": 0, "y": 0}
}])
```

规则：

- `tasks.length=1`。一个 task 只对应一个物品/建筑/植物/动物/角色，一个节点不能映射给两个实体；两个实体要两次准备，或明确拆成两批并分别记录成功与失败；
- `prepare` 只提交意图，不硬编码模型名、画幅、分辨率、质量或数量（除非当前 schema 明确要求这些意图字段）；
- 已有图片节点优先放 `source_node_ids`；用户上传素材放 `reference_images` 对应字段；空引用不要传；
- 风格基准、评审报告等 text 节点的内容摘要写进 `prompt`，节点 ID 只做来源记录。

### 阶段 3 · 逐项选参

每次 `canvas_generation_select` 只处理最新响应要求的一个参数类别，值逐字复制当前 task 的 options，并使用最新 `revision`。直到返回 `status="ready_to_generate"` 才允许提交。用户指定但当前 options 里没有的选项，直接说明“当前不可用”，按可用项或用户选择继续，不要编造模型名与参数。

### 阶段 4 · 提交

```text
canvas_media_create(plan_id=<最新 plan_id>, revision=<最新 revision>)
```

请求键集合严格等于 `plan_id` + `revision`，不要附加 `tasks`、`model_name`、`duration`、名称或工作项 ID。该调用触发平台原生扣费确认，已由平台确认卡负责，不要再加一层“确认生成吗”的聊天确认。

提交后立刻做三件事：检查该 task 是否出现在 `failures`；有真实 `node_id` 就完成两步命名；回执告知“已创建并提交，生成中，不算完成”。

### 阶段 5 · 状态查询与验收

```text
canvas_status_manage(operation="get", node_id=<真实 node_id>)
```

- 图片完成 = `task_status="completed"` 且 `cover_url` 非空；视频化/序列化产物不在本 Skill 范围；
- 完成之后才进入内容质量门（第 9 节），通过写 `accepted`，不通过改名并写 `rejected`；
- **后处理能力说明**：1% 纯黑底去掉 alpha 白边、缩到 64×64 复核、放进场景截图对比香草素材，这三步通常不是画布生成能力的一部分。能做就做；不能做时按 `degraded` 交付，并在回执里明确写出“用户在图像编辑器中需手动完成哪三步”，不要说已经做完。

### 阶段 6 · 评审报告（有评审结论时）

把结论写成文字节点 `<素材名>像素美术评审报告`，正文含：被评审节点 ID 与版本、结论（通过/不通过）、逐条质量门结果（是/否/未验证）、必须修改项、`status`。无法从画布内容确认的事实标 `unverified`，不要补猜。

## 7. 状态与成功证据

```text
drafted     已写好风格基准/提示词，但尚未落画布
saved       文字节点已创建且有 canvas_node_id + asset_node_id
submitted   图片节点已创建并提交任务
generating  异步处理中
generated   task_status=completed 且 cover_url 非空
accepted    生成完成且通过内容质量门，允许下游引用
rejected    节点保留但质量门未通过，改名 未采用-*
stale       上游版本变化，不可继续引用
partial     批量中部分实体成功
blocked     缺能力/输入/权限，或不可重试错误
degraded    已降级交付（如无后处理、无图片节点），核心能力不完整
```

三种断言必须分别取证，不能互相顶替：

- 有 `task_key` ≠ 有画布节点；
- 有 `node_id` ≠ 生成完成（可能落在 `failures` 里：节点存在、任务未启动）；
- 有 `cover_url` ≠ 质量通过。

## 8. 失败、降级与重试

| 情况 | 必须做什么 | 不得做什么 |
| --- | --- | --- |
| 可重试工具错误 | 保留原意图，只重新准备当前单项，换用尚未尝试的兼容选项 | 假装已生成、盲目整批重跑 |
| 积分不足 | 停止当前媒体任务，报告平台真实错误 | 自动换模型循环扣费 |
| 参考图无效 | 删除可选引用，或要求重新上传必需素材 | 猜 URL、把 text 节点当图片 |
| 参数不被 schema 接受 | 只修正被拒字段后重新 `prepare` | 把错误归因于“风格不对” |
| 内容审核失败 | 说明需要调整的内容范围 | 用拆词、编码或隐喻绕过审核 |
| 部分成功 | 逐项记录真实节点与失败原因，只补失败项 | 用“整批成功”覆盖失败项 |
| 节点已建但任务未启动 | 保留节点，状态停在 `pending`/`blocked` | 回执“生成中”、推进下游 |
| 仍 `processing` | 等用户下次检查，复用已有节点 ID | 重复提交同一任务 |
| 画布能力缺失 | 交付结构化文字 + 明确说明未落画布，标记 `blocked`/`degraded` | 声称已落画布 |
| 自动命名失败 | 报真实节点 ID，停止把该节点作为正式输入 | 再生成一张图解决命名 |
| 无法执行 1% 黑底/64×64 复核 | 标记 `degraded`，列出用户手动步骤 | 声称白边已处理 |

重试使用新 task key 后缀（如 `PROP_01_R1`），保留旧节点与失败记录；只重做失败或被拒收的那一项，不重做已通过的上游产物。重新生成必须重新走 `prepare → select → media_create`，并重新经过平台扣费确认。

**stale 传播**：改风格基准 → 所有下游图片与评审报告过期；改某实体强度等级或描边类别 → 仅该实体下游过期；改画布尺寸规范 → 所有图片过期。stale 节点不得放进新的 `source_node_ids`，也不能同时混用同一资产的两个版本。

## 9. 用户接力

每次阶段结束、异步提交、失败或等待选择时，回执固定四行：

```text
当前状态：<真实状态>
证据：<真实节点 ID / cover_url / task_status / 错误；没有则写“尚未创建节点”>
下一流程：<当前节点质量验收 / 下一个相邻阶段>
请操作：<在哪里操作，以及输入“继续”“重试”或“停止”后会发生什么>
```

示例：

```text
当前状态：“熔炉像素建筑图”已创建并提交，正在生成；目前还不能算完成。
证据：node_id=<真实 ID>，task_status=processing，名称已确认。
下一流程：64×64 可读性与强度层级验收。
请操作：画布出现图片后输入「继续」，我会查询真实状态、检查黑描边是否 2–3 px 且不抢角色视线，并交付评审报告。
```

不要只写“稍后继续”“生成完成后质检”“通过后进入下一阶段”“节点正在生成”“还有什么需要”。用户已输入“继续”或明确动作词时，直接执行上一轮承诺的相邻阶段，不要再问规格确认、命名确认或“是否生成”。

额外的确认门只允许三种：首次创作需确认目标时长/尺寸；参考图不规范需确认修复或拆分范围；`canvas_media_create` 的平台原生扣费确认。

## 10. 质量验收

工具成功不等于内容正确。先按第 7 节确认 `generated`，再逐条回答下面的问题（领域门，是/否）：

- [ ] 缩到游戏尺寸（64×64 或实际尺寸）后，还能认出它是什么吗？
- [ ] 剪影是否独特，不会与同类物体混淆？
- [ ] 描边粗细/颜色是否符合它的强度等级（角色 2–3 px 纯黑、物品建筑 2–3 px 黑实线、植物深绿或无描边）？
- [ ] 有没有宽度小于 3 px 且低对比的无效细节？
- [ ] 有没有多余的黑色内线（本应交给明暗处理）？
- [ ] 是否加了约 1% 黑底、边缘无白边？（画布能力做不到时标 `unverified`，不判通过）
- [ ] 在一屏上百个物体中，它会不会抢走主角（Pawn）的注意力？
- [ ] 它是否在替玩家把故事“讲完”，而不是留下想象空间？
- [ ] 画幅是否 1:1、构图是否用补白而非移动主体、主体是否被裁切？
- [ ] 有没有输入不支持的物体、文字、水印、Logo 或背景事实？

通用门：目标可见、主体与动作无遗漏；引用的素材版本正确；输出数量与顺序与输入一致；能直接供下游使用，不需要用户手工猜对应关系。

质量不通过时保留节点便于追溯，改名为 `未采用-<目标名称>-<主要原因>`，标记 `rejected`，不进入下游引用链，并给出“重试 / 停止”两个动作词。

## 11. 示例与验收用例

### 用例 A · 正常路径（物品）

```text
用户：帮我把这个铜制怀表做成 RimWorld 风格的物品图标，参考 img:1。

阶段 0：判定为 PROP_01@v01，强度等级=物品（2–3 px 黑实线描边）。
阶段 1：画布无风格基准 → canvas_text_create
        名称“全局美术风格基准”，正文含五条标准/描边表/128×128/1% 黑底/3 px 门槛/负向边界；
        返回 canvas_node_id 与 asset_node_id 齐全 → STYLE_01@v01 saved。
阶段 2：canvas_generation_prepare(tasks=[{
          task_key: "PROP_01_ICON", node_type: "image",
          prompt: "RimWorld 风格像素物品图标：铜制怀表，单一实体，斜俯视小物件视角…
                   §五条标准摘要 §物品 2–3 px 黑实线描边 §128×128 1:1 画布
                   §主体居中，边缘补白，不裁切 §负向：写实纹理/渐变/高光/内线/水印/文字",
          reference_images: ["img:1"]
        }])
阶段 3：逐类 select，直到 status="ready_to_generate"。
阶段 4：canvas_media_create(plan_id, revision) → 不在 failures，node_id=<真实>；
        两步命名“铜制怀表像素物品图”；回执：已提交、生成中、请稍后输入「继续」。
阶段 5：用户输入“继续”→ canvas_status_manage(get)
        → completed 且 cover_url 非空 → generated；
        → 逐条通过第 10 节领域门 → accepted；后处理不可用时标 degraded 并列出手动三步。
```

### 用例 B · 失败与部分成功路径

```text
用户：一次给我夜光苔、雪原狼、熔炉三张图。

正确做法：
1. 拆成三个实体：PLANT_01 / ANIM_01 / BLD_01，各自独立 prepare（tasks.length=1）；
2. 三次 select + media_create，分别检查 failures；
3. 假设 ANIM_01 在 failures 中（节点存在、任务未启动）：保留节点，状态 pending/blocked，
   只对 ANIM_01 用新 task key ANIM_01_R1 重试，不重跑 PLANT_01 与 BLD_01；
4. 若 BLD_01 生成但描边过粗抢了画面：改名“未采用-熔炉像素建筑图-描边过粗破坏层级”，
   标记 rejected，与用户确认后重试；
5. 回执写清整体 partial：成功几项、失败几项、各自真实节点 ID、下一流程与动作词。
```

### 验收最小用例

1. 正常路径：单实体物品图从文字基准到 `accepted`，含两步命名与 `cover_url` 证据；
2. 失败路径：一次 `failures` 命中、一次质量门不通过改名、一次缓存引用（stale 节点）被拒绝；
3. 降级路径：画布不可用时标记 `blocked`，并只交付结构化文字，不声称已落画布；
4. 引用路径：把 text 节点当图片引用被拒绝，改为写入 prompt。

## 12. 常见错误（含 Updream 侧误用）

- 把图标当插画来画：细节堆满、缩小后成一团噪点。
- 给植物画粗黑边，植被比角色还跳，破坏强度层级。
- 用黑色内线勾结构，画面变脏、变“贴纸感”。
- 用超大画布或过小像素，导致物品在游戏里比例失衡。
- 用发光、强渐变、锐利高光吸引视线，把注意力从叙事上引开。
- 把聊天文本、Markdown 文件、本地路径当成“已落画布”。
- 把 text 节点（风格基准/评审报告）塞进 `reference_images` 或 `source_node_ids`。
- 一个 task 混装多个实体，事后无法判断哪个节点属于哪个物体。
