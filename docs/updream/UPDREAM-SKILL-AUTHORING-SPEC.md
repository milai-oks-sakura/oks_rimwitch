# Updream Skill 撰写规范

版本：v1.0  
适用对象：为 Updream Agent 编写、移植或维护 Skill 的外部创作者  
适用范围：需要在 Updream 中读取输入、生成内容、把产物落到画布、继续编辑或交付结果的 Skill

## 1. 这份规范解决什么问题

普通 Codex、Claude 或其他 Agent 中可运行的 Skill，通常把聊天回复、Markdown 文件和生成结果视为交付物。Updream 的运行模型不同：用户可见的正式产物必须进入画布，媒体生成是异步的，节点创建、任务提交、生成完成和内容验收是不同状态。

因此，Updream Skill 不能只写“分析后输出提示词”，也不能只依赖普通文件或聊天文本。Skill 必须同时说明：

- 哪些内容是正式产物，使用哪一种画布节点保存；
- 哪些输入可以作为真实引用，怎样把上游节点传给下游任务；
- 如何按照当前工具 schema 创建文本、图片或视频；
- 什么证据才算创建成功、提交成功、生成完成和质量通过；
- 工具失败、部分成功、异步处理中、用户取消时如何停留和恢复；
- 每次暂停时用户要在哪里操作、输入什么动作词才能继续。

本规范是作者约束，不是要求每个 Skill 都实现完整视频流水线。只实现文字、图片、视频或分析中的一部分时，仍须遵守对应部分的画布和证据规则。

## 2. Updream 与通用 Agent 的边界

### 2.1 运行时优先级

实际执行时以当前 Updream 工具注册表和实时参数 schema 为准。参考 Skill、历史模型档案、示例 JSON 和文档中的旧字段只能帮助理解意图，不能覆盖实时 schema。

推荐在 Skill 中明确写出以下边界：

```text
本 Skill 在 Updream 中运行时：
1. 文字正式产物使用 canvas_text_create。
2. 图片/视频正式产物使用 canvas_generation_prepare
   -> canvas_generation_select -> canvas_media_create。
3. 节点状态使用 canvas_status_manage(operation="get") 查询。
4. 媒体节点创建后使用 canvas_status_manage(operation="update") 自动命名。
5. 不能调用的能力必须报告 blocked/degraded，不用聊天文本冒充画布产物。
```

### 2.2 Updream 业务能力与通用内部平台能力

Skill 需要区分业务入口：

- Updream 业务查询、画布、生成、技能社区和业务数据使用 `updream` 能力；
- 通用日志、RDS、GitLab、Caster、TAPD、Zhiliao 等内部平台能力使用 `bilirt` 能力；
- 不要因为某个内部平台名称出现在示例中，就把它写成 Updream 专用命令；
- 不要硬编码主机路径、旧版脚本路径、固定模型名或固定价格。

如果 Skill 只处理画布生成，就不要在顶层加载无关的数据库、日志或发布能力。能力按场景按需读取，缺失时提供明确降级路径。

### 2.3 不要把会话路由写成通用 Plan

`current_stage`、`pending`、`next_stage`、`Q0/S1` 等字段可以用于当前会话内判断下一项画布产物，但不能自动转换成 Updream 通用 Plan、工作项、Checklist 或步骤状态。除非用户明确要求管理项目计划，否则不要创建或维护这类对象，也不要生成类似 `w1`、`w7_board` 的工作项 ID。

媒体准备返回的 `plan_id` 是本轮媒体选参令牌，只能原样传给同一轮 `canvas_generation_select` 和 `canvas_media_create`；不要把它当成通用业务 Plan。

## 3. Skill 文件必须写清楚什么

一个可审核的 Updream Skill 至少包含以下内容。简单 Skill 可以合并章节，但不能省略语义。

```text
---
name: <稳定、可读、唯一的 skill 名>
description: <触发范围、Updream 产物和重要边界>
---

# <Skill 名>

## 目标
## 触发与不触发
## 输入与真实引用
## 画布产物与节点命名
## 执行流程
## 状态与成功证据
## 失败、降级与重试
## 用户接力
## 质量验收
## 示例与验收用例
```

`description` 要描述用户意图和最终产物，不要只写专业领域名。例如“写一套分镜提示词”无法说明是否要落画布；应写成“将用户视频拆解为真实关键帧节点，并创建逐帧分析文本节点”。

顶层正文应先给最高优先级的运行边界，再给目标和流程。不要把关键约束藏在十几个引用文件深处，也不要把同一条工具协议复制成互相矛盾的多个版本。

## 4. 画布产物规范

### 4.1 什么必须落到画布

只要是用户会在后续流程继续使用、查看、编辑或引用的正式产物，都必须创建为真实画布节点。常见分类如下：

| 产物 | 节点类型 | 推荐创建方式 | 完成的最低证据 |
| --- | --- | --- | --- |
| 剧本、方案、设定、分镜文字、分析报告 | text | `canvas_text_create` | 每项有真实 `canvas_node_id` 与 `asset_node_id` |
| 图片、关键帧、角色图、场景图、故事板 | image | `canvas_generation_prepare` → `select` → `media_create` | 有真实 `node_id`，任务未出现在 `failures`，完成后有 `cover_url` |
| 视频、动画、成片 | video | `canvas_generation_prepare` → `select` → `media_create` | 有真实 `node_id`，任务完成后有 `video_url` |
| 已有用户上传素材 | image/video/audio 或平台附件 | 使用真实上传句柄或已有节点 | 当前工具能解析该引用 |

聊天里的长文、Markdown 文件、本地图片路径、包内文件名和模型臆测 URL 都不能替代正式画布产物。若画布能力不存在，必须写 `canvas_delivery=blocked` 或 `degraded`，同时交付可复制文本或真实 URL，但不能声称“已落画布”。

### 4.2 文字节点怎么写

新写的剧本、说明、表格、分析和分镜文字统一使用 `canvas_text_create`。正文是最终可供下游使用的完整内容，不要只写摘要、占位符或“见聊天记录”。

推荐调用形态如下；实际字段以当前 schema 为准：

```text
canvas_text_create(
  tasks=[
    {
      "name": "<语义化节点名>",
      "text_content": "<完整正文>",
      "source_node_ids": ["<真实上游节点 ID>"]
    }
  ]
)
```

写入正文时遵守四条规则：

1. 节点名表达产物用途，不使用“文本1”“结果”“草稿”等无意义名称；
2. 正文包含目标、范围、输入依据、稳定 ID、版本、依赖和可执行内容；
3. `source_node_ids` 只放真实存在且确实被引用的上游节点，正文中不要嵌入 `img:1` 等聊天句柄；
4. 工具返回必须同时有 `canvas_node_id` 和 `asset_node_id` 才能说文字已落画布。缺任一项，状态只能是 `blocked` 或 `partial`。

### 4.3 文字节点正文模板

可按产物类型裁剪字段，但保留可追溯信息：

```text
产物类型：<script / design / storyboard / report>
产物 ID：<SCRIPT_01 / LOC_01 / S01-SH01>
版本：v01
来源：<用户输入、上游节点 ID、视频或图片引用>
目标：<这份节点供谁、在下一步做什么>
依赖版本：<STYLE_01@v01、CHAR_01@v01 ...>

正文
<完整可执行内容，不写“略”或“见上文”>

验收要点
- <可检查事实 1>
- <可检查事实 2>

状态：drafted / accepted / stale
```

有多个镜头、实体或事件时，使用稳定 ID 一一对应。例如场景用 `S01`，镜头用 `S01-SH01`，角色用 `CHAR_01`，地点用 `LOC_01`。稳定 ID 写入正文和 prompt，显示名称保持人类可读。

### 4.4 节点命名规则

节点名称应在创建前确定，能够让用户在画布中直接判断用途和归属。推荐约定：

| 产物 | 名称模板 | 例子 |
| --- | --- | --- |
| 主剧本 | `剧本` | `剧本` |
| 资产登记 | `美术资产清单` | `美术资产清单` |
| 全局风格 | `全局美术风格基准` | `全局美术风格基准` |
| 角色图 | `<角色名>角色三视图` | `林默角色三视图` |
| 场景说明 | `<场景名>场景空间设计说明` | `旧车站场景空间设计说明` |
| 场景图 | `<场景名>场景空间设定板` | `旧车站场景空间设定板` |
| 道具图 | `<道具名>道具设定图` | `铜制怀表道具设定图` |
| 故事板 | `场<序号>-<场景名>分镜故事板` | `场01-旧车站分镜故事板` |
| 关键帧 | `视频关键帧<序号>` | `视频关键帧03` |
| 视频 | `视频初版` 或 `<作品名>视频初版` | `雨夜车站视频初版` |

媒体创建接口通常不能直接在请求中传显示名称。拿到真实 `node_id` 后，必须在同一轮使用 `canvas_status_manage(operation="update")` 完成预览和提交两步命名：

```text
canvas_status_manage(operation="update", node_id=<真实 ID>,
                     name="<目标名称>", confirmed=false)
canvas_status_manage(operation="update", node_id=<同一 ID>,
                     name="<目标名称>", confirmed=true)
```

命名失败时，节点仍可保留为生成结果，但不能作为正式下游输入；报告真实节点 ID 和命名失败状态。

### 4.5 画布布局

需要主动布置节点时，布局应服务于扫描和追溯：

- 上游文字或源素材放在左侧/顶部；
- 下游图片、关键帧或视频按流程方向排列；
- 同一场景或同一镜头的节点保持相邻；
- 多个节点采用稳定尺寸和固定间距，标题变长不能导致布局跳动；
- 已存在节点不重复创建，不用补建覆盖用户节点；
- 真实节点 ID 与位置一并记录，避免只靠名称匹配。

如果当前画布 API 不支持位置或尺寸字段，不要伪造字段；保留语义名称和依赖关系即可。

## 5. 媒体生成调用规范

### 5.1 唯一调用链

新图片和视频必须使用以下顺序：

```text
canvas_generation_prepare(tasks=[...])
  -> canvas_generation_select(...)
  -> canvas_generation_select(...)
  -> ...
  -> canvas_media_create(plan_id=<最新值>, revision=<最新值>)
```

`prepare` 只提交任务意图，`select` 只从当前返回的 options 原样选择参数，`media_create` 只提交最新 `plan_id` 和 `revision`。不要在 `prepare` 里硬编码模型、比例、分辨率、时长、质量或输出数量，除非当前实时 schema 明确要求这些意图字段。

### 5.2 任务意图模板

```text
{
  "task_key": "<唯一稳定任务键>",
  "node_type": "image" | "video",
  "prompt": "<完整、可执行、包含资产版本和负面边界的提示词>",
  "reference_images": ["<真实图片句柄或 URL>"],
  "reference_videos": ["<真实视频句柄或 URL>"],
  "reference_audios": ["<真实音频句柄或 URL>"],
  "source_node_ids": ["<真实、已完成、版本匹配的 image/video 节点 ID>"],
  "depends_on": ["<真实任务依赖>"],
  "position": {"x": 0, "y": 0}
}
```

只提交当前 schema 接受的字段。空引用不要传；`depends_on` 表示任务之间必须先后完成的真实依赖，不能代替普通参考图。

### 5.3 真实引用规则

可以作为引用的值只有：

- 当前对话中真实存在的用户上传句柄；
- 平台返回且当前工具可读取的真实 URL；
- 已存在、已完成、内容验收通过的画布媒体节点 ID；
- 本轮前序任务真实返回的结果。

不能使用本地路径、压缩包内文件名、Markdown 图片名、旧对话中记住的 ID 或自行拼出的 URL。已有画布节点优先放在 `source_node_ids`；用户上传素材按当前 schema 的 `reference_images`、`reference_videos` 或 `reference_audios` 传递。

媒体任务的 `source_node_ids` 只传实际需要的 image/video 节点。不要把剧本、资产清单、风格基准、文字分镜等 text 节点当作图片引用；这些内容应完整写进 prompt，并通过文字节点 ID 记录来源。

### 5.4 逐项选参

每次 `canvas_generation_select` 只处理最新响应要求的一个参数类别，值必须逐字复制对应 task 当前的 options，并使用最新 `revision`。直到返回 `status="ready_to_generate"` 才能提交。

不要从历史 Skill 复制已失效的模型名、画幅、分辨率、时长或数量。用户指定的选项只有在当前 options 存在时才能使用；不存在就说明该选项当前不可用，按可用项或用户选择继续。

### 5.5 提交与扣费

`canvas_media_create` 的请求键集合必须严格等于：

```text
{ "plan_id": <ready_to_generate 返回的 plan_id>,
  "revision": <ready_to_generate 返回的 revision> }
```

不要附加 `tasks`、`model_name`、`duration`、名称、工作项 ID 或旧版参数。该调用会触发 Updream 平台原生扣费确认。除输入图处理范围这类流程决策外，不要再用聊天问题模拟第二次生成确认。

提交前可以向用户披露产物名称、数量、当前选定模型、画幅/时长和平台给出的预计积分；实际消耗必须说明以平台原生确认卡和最终扣除为准。价格不可得时继续使用当前合法 options，不要把价格查询变成生成前置门槛。

### 5.6 批量与实体隔离

`tasks` 支持数组不代表所有任务都可以混在一起：

- 角色三视图、场景设定板、关键道具图和输入图轻修复，默认每次只准备一个实体，`tasks.length=1`；
- 一个 task 只对应一个角色、场景或道具，一个节点不能映射给两个实体；
- 故事板按一个场景或连续镜号范围处理；
- 视频关键帧按一个 `shot_id` 处理；
- 只有工具明确返回单次载荷上限时才拆批，每个批次独立记录成功和失败。

## 6. 状态、证据与回执

### 6.1 不同状态不能混用

建议在会话记录中使用以下状态：

```text
drafted       已在上下文中写好，但尚未落画布
saved         文字节点已创建并有真实节点证据
submitted     媒体节点已创建并提交任务
generating    任务已启动，正在异步处理
generated     任务完成且有真实媒体 URL
accepted      生成完成并通过内容质量门
rejected      节点保留，但质量门未通过
stale         上游版本变化，当前节点不可继续引用
partial       批量结果部分成功
blocked       缺少能力、输入、权限或不可重试错误
degraded      已按降级方案交付，核心能力不完整
```

`canvas_media_create` 返回节点 ID 只证明节点创建或提交结果，不能直接写成“已生成”。必须先检查该 task 是否在 `failures` 中：有节点但在 `failures` 中表示节点存在、任务未启动。

媒体完成最低证据：

- 图片：`canvas_status_manage(operation="get")` 返回 `task_status="completed"` 且 `cover_url` 非空；
- 视频：返回 `task_status="completed"` 且 `video_url` 非空；
- 文字：创建结果同时含 `canvas_node_id` 和 `asset_node_id`。

完成证据仍不等于内容质量通过。通过质量门后才把状态写为 `accepted`，并允许下游引用。

### 6.2 依赖、版本和 stale

对可复用资产分配稳定 ID 和版本：

```text
CHAR_01@v01   角色
LOC_01@v01    场景
PROP_01@v01   道具
STYLE_01@v01  全局风格
S01-SH02@v01  镜头
```

每个下游正文或 prompt 记录 `depends_on_versions`。上游事实变化时传播 `stale`：

- 改剧本角色、场景或关键剧情：资产清单和全部下游过期；
- 改全局风格：图片、故事板、关键帧和视频过期；
- 改某角色：仅引用该角色的下游过期；
- 改某场景：该场景的分镜、故事板、关键帧和视频过期；
- 改某道具：只让引用它的镜头链路过期；
- 改文字镜头：对应故事板、关键帧和视频过期。

禁止把 stale 节点放进新的 `source_node_ids`，也不能同时混用同一资产的两个版本。

### 6.3 用户接力回执

每次阶段结束、异步提交、失败或等待选择时，回执必须回答三个问题：当前是什么状态、下一流程是什么、用户现在输入什么会继续。推荐固定结构：

```text
当前状态：<真实状态>
证据：<真实节点 ID、URL、状态或错误；没有则写“尚未创建节点”>
下一流程：<当前节点质量验收 / 下一个相邻阶段>
请操作：<在哪里操作，以及输入“继续”“重试”或“停止”后会发生什么>
```

标准示例：

```text
当前状态：“旧车站场景空间设定板”已创建并提交，正在生成；目前还不能算完成。
证据：node_id=<真实 ID>，task_status=processing。
下一流程：场景空间设定板质量验收。
请操作：画布出现图片后，请输入「继续」；我会查询真实状态并检查四区是否为同一空间，通过后进入文字分镜。
```

不要只写“稍后继续”“生成完成后质检”“通过后进入下一阶段”“节点正在生成”或“还有什么需要”。这些句子没有给出可执行动作。

除以下情况外，不要增加额外确认门：

- 首次创作需要确认目标时长；
- 输入图不规范，需要确认修复/拆分范围；
- `canvas_media_create` 的平台原生扣费确认。

用户已经输入“继续”或明确动作词时，直接执行上一轮承诺的相邻阶段，不要再问一次规格确认、命名确认或“确认生成”。

## 7. 质量验收怎么写

Skill 必须把“工具成功”与“内容正确”分开。质量门至少应可由图片、视频或文本的实际内容判断，不能只写“模型输出正常”。

通用质量门：

- 任务目标可见，主体和动作没有被遗漏；
- 引用的角色、场景、道具和风格版本正确；
- 输出数量、镜头/事件覆盖和顺序与输入一致；
- 没有未经输入支持的角色、文字、水印、Logo 或背景事实；
- 内容能供下一阶段直接使用，不能要求用户手工猜测对应关系。

领域质量门示例：

- 角色三视图：同一身份、正面/右侧/背面为真实 0/90/180 度、同尺度全身、服装和材质一致；
- 场景设定板：俯视布局和三个透视机位属于同一空间，至少四个固定锚点能互相对应；
- 故事板：逐格匹配镜头 ID、顺序、景别、动作和资产版本；
- 视频关键帧：单幅成片构图，不带故事板网格和标签，主体完整且为运动方向留空间；
- 视频：身份、服装、地标、道具状态、动作因果和运镜连续，无非预期复制或肢体破坏；
- 拉片分析：每条结论能回溯到真实时间、帧或节点，无法看清时标记 `unverified`，不补猜事实。

质量不通过时保留节点以便追溯，自动改为 `未采用-<目标名称>-<主要原因>` 或同等语义名称，标记 `rejected`，不要让它成为下游引用。重新生成必须重新 `prepare → select → media_create`，并重新走平台扣费确认。

## 8. 失败、降级和重试

每个 Skill 至少定义以下情况：

| 情况 | 必须做什么 | 不得做什么 |
| --- | --- | --- |
| 工具返回可重试错误 | 保留原意，重新准备当前单项，选择尚未尝试的兼容选项 | 假装已经生成、盲目重复整批 |
| 积分不足 | 停止当前媒体任务，报告平台真实错误 | 自动换模型循环扣费 |
| 引用无效 | 删除可选引用，或要求重新上传必需素材 | 猜测 URL、把 text 节点当图片 |
| 参数不支持 | 只修正 schema 不接受的字段，再重新 prepare | 把错误归因于用户风格 |
| 内容审核失败 | 说明需要调整的内容范围 | 通过拆词、编码或隐喻绕过审核 |
| 部分成功 | 逐项保存真实节点和失败原因，只补失败项 | 用“整批成功”覆盖失败项 |
| 节点创建成功但任务未启动 | 保留节点，状态停在 pending/blocked | 回执“生成中”或推进下游 |
| 异步仍 processing | 等用户下一次检查，复用已有节点 ID | 重复提交同一任务 |
| 画布能力缺失 | 交付真实 URL/结构化文本并标记 degraded/blocked | 声称已落画布 |
| 自动命名失败 | 报真实节点 ID，停止把该节点作为正式输入 | 再生成一张媒体来解决命名 |

重试使用新的 task key 后缀，例如 `SHOT_03_R1`，保留旧节点和失败记录。除非用户明确要求，重试只处理失败或拒收的那一项，不重做已通过的上游产物。

## 9. 输入、输出和引用的最小数据契约

外部 Skill 建议在内部维护一个轻量记录，不必把所有字段展示给用户：

```text
asset_id:
asset_version:
display_name:
target_node_name:
type: text / image / video / audio
source_refs: <真实上传句柄、URL 或画布节点 ID>
depends_on_versions:
canvas_node_id:
asset_node_id:
task_key:
task_status:
result_url:
generation_status:
quality_status:
failure_code:
next_user_action:
```

不要把“有 task_key”当成“有画布节点”，不要把“有 node_id”当成“生成完成”，也不要把“有 URL”当成“质量通过”。这三个断言必须分别由真实证据支持。

## 10. 从通用 Skill 移植到 Updream

移植已有 Skill 时，按下面顺序检查：

1. 找出所有“输出到聊天/文件/本地路径”的句子，判断它们是否应改为画布正式产物；
2. 把图片和视频的直接生成调用改成 `prepare → select → media_create`，删除硬编码模型和旧版参数；
3. 把 `@图片1`、`img:1`、文件名等展示占位符映射为真实 `reference_*` 或 `source_node_ids`；
4. 给所有会复用的角色、场景、道具、镜头和风格分配稳定 ID 与版本；
5. 为每个产物定义节点名称、成功证据、质量门和失败状态；
6. 把“生成完成”改为基于 `canvas_status_manage(get)` 和真实结果 URL 的断言；
7. 为异步、部分成功、用户取消、输入缺失和画布不可用补充降级路径；
8. 检查每个停顿是否告诉用户“下一流程、在哪里操作、输入什么动作词”；
9. 删除通用 Plan、工作项、Checklist 和平台不支持的确认门，除非用户明确要求这些业务对象；
10. 用真实工具 schema 和至少一组失败样例做 smoke test。

## 11. 最小可用示例

下面是一个“用户给一张图，生成一张角色参考图并落到画布”的最小结构。它展示规范，不固定实际字段；执行时必须以当前工具 schema 为准。

```text
触发：用户说“把这张图整理成角色参考图”并提供真实 img:1。

输入检查：确认 img:1 在当前上下文可读取；若不可读，状态 blocked，要求重新上传。

产物登记：
- asset_id=CHAR_01
- asset_version=v01
- target_node_name=角色名角色三视图

准备：
canvas_generation_prepare(tasks=[{
  task_key: "CHAR_01_VIEWS",
  node_type: "image",
  prompt: "同一角色的正面、右侧纯侧面、背面三视图；...",
  reference_images: ["img:1"]
}])

选参：逐轮从当前 options 选择可用模型、画幅、质量和数量，使用最新 revision。

提交：
canvas_media_create(plan_id=<最新 plan_id>, revision=<最新 revision>)

提交后：
- 检查 task 是否出现在 failures；
- 若有真实 node_id，立即执行两步语义命名；
- 回执“节点已创建，生成中”，提示用户在画布出现结果后输入“继续”。

验收：
canvas_status_manage(operation="get", node_id=<真实 node_id>)
- 只有 completed + 非空 cover_url 才算生成完成；
- 再检查三视图身份、0/90/180 度、同尺度、无其他人物和无水印；
- 通过后 generation_status=accepted，允许下游引用；
- 不通过则 rejected，改名并提示“重试”或“停止”。
```

## 12. 发布前审核清单

提交给 Updream 适配审核前，作者应逐项回答“是”或提供降级说明：

- [ ] `description` 写清触发意图、正式产物和主要边界；
- [ ] 每个正式文字产物使用 `canvas_text_create`；
- [ ] 每个正式媒体产物使用当前合法的 `prepare → select → media_create`；
- [ ] 没有把聊天文本、普通文件、本地路径或虚构 URL 当成画布证据；
- [ ] 文本创建同时核对 `canvas_node_id` 与 `asset_node_id`；
- [ ] 媒体完成同时核对完成状态和真实 `cover_url`/`video_url`；
- [ ] 节点名称语义明确，媒体节点创建后自动完成两步命名；
- [ ] 真实引用与展示占位符已经分离并正确映射；
- [ ] 有稳定 ID、版本、依赖和 stale 传播规则；
- [ ] 已定义质量门，工具成功不直接等于内容通过；
- [ ] 已定义可重试失败、不可重试失败、部分成功、取消和能力缺失；
- [ ] 每次等待都给出下一流程、用户动作和可直接输入的动作词；
- [ ] 没有无必要的通用 Plan、工作项或重复确认门；
- [ ] 至少测试一次正常路径和一次失败/部分成功路径；
- [ ] Skill 缺少核心工具时会诚实标记 `blocked` 或 `degraded`。

### 审核结论的推荐写法

```text
通过：正式产物、调用链、真实引用、状态证据和失败恢复均符合 Updream 运行契约。

有条件通过：核心流程可运行，但 <具体缺口> 只能降级交付；Skill 不得声称该分支已落画布/已完成。

不通过：<具体缺口> 会让聊天文本、默认节点、虚构引用或异步提交被误报为正式结果；修复后再测。
```

## 13. 一句话原则

在 Updream 中，Skill 的每一个“完成”都必须能被用户在画布里看到、被下游工具用真实 ID 引用、被状态接口和结果 URL 复核，并且在失败时有诚实可执行的下一步。
